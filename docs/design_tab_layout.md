# 検討: 複数タブ構成への変更

ステータス: **保留（今後の判断事項）**  
起票日: 2026-05-26

---

## 概要

現行の単一結果テキストボックスを `TabControl` に置き換え、  
機能ごとに結果タブを分ける構成への変更について検討した。

---

## 想定する構成

```
結果エリア (TabControl)
├── 全結果    ← 全機能の出力を時系列で集約
├── Ping      ← Ping 確認の結果のみ
├── TCP       ← TCP ポート確認の結果のみ
├── Tracert   ← Tracert の結果のみ
└── DNS       ← DNS 確認の結果のみ
```

- 各ボタン実行時に該当タブへ追記し、そのタブへ自動切り替え
- 「全結果」タブには全機能の出力を集約（現行の `LogBuffer` 相当）
- 左パネル（宛先入力・ポート入力・ボタン群）は変更なし

---

## メリット

- 機能ごとに結果が分離され、再確認・コピーがしやすい
- 複数機能を連続実行したときに結果が混在しない
- 画面の情報密度が下がり、視認性が向上する

## デメリット・注意点

- タブごとに独立した `TextBox` と `StringBuilder` が必要になり、コードが現状比 +50 行程度増加する
- `LogBuffer` を「全結果用」と「タブ別」に分けて管理する必要がある
- 保存処理の設計判断が生じる（下記参照）

---

## 保存処理の設計判断（未決）

タブ構成にした場合、保存対象をどうするかの選択肢がある。

| 案 | 内容 | 備考 |
|----|------|------|
| A | 「全結果」タブの内容を 1 ファイルに保存（現行と同等） | シンプル。推奨候補 |
| B | 各タブを個別ファイルに保存（タブ名をファイル名に付与） | ファイル数が増えるが機能別に分離できる |
| C | 保存時に対象タブをユーザーが選択 | 柔軟だが UI が複雑になる |

プロトタイプ段階では **案A** が最もシンプルで変更量も少ない。

---

## 実装コスト見積もり

| 項目 | 変更内容 |
|------|---------|
| GUI 初期化 | `TabControl` + 5 つの `TabPage` + 各 `TextBox` の生成に変更 |
| 結果追記関数 | `Add-Result` にタブ選択ロジックを追加 |
| 保存処理 | `LogBuffer` の参照先を整理（案 A なら変更最小） |
| `LogBuffer` 管理 | タブ別 `StringBuilder` を追加、またはグローバル 1 本のまま維持 |

既存の処理関数（`Invoke-*`）自体の変更は不要。

---

## 判断時の確認事項

実装に進む場合、以下を事前に確認すること。

1. 保存対象は「全結果 1 ファイル」で良いか（案 A）
2. タブ切り替えは「ボタン実行時に自動切り替え」で良いか
3. 結果クリアは「全タブ一括クリア」か「表示中タブのみ」か
